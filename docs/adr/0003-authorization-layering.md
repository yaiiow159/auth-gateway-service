# ADR-0003：授權分層 —— 網關粗粒度、服務細粒度，預設 fail-closed

- 狀態：已採納
- 日期：2026-08-28

## 背景

「授權該放在哪一層」是這類架構最容易做錯的決定。放太多在網關，網關會逐漸變成需要
理解所有業務規則的巨石；放太少，每個服務各自實作，遲早有人漏寫。

## 決策

**依「判斷所需的資訊」來切分，而不是依「方便」來切分。**

| 層級 | 判斷內容 | 依據 | 實作 |
|------|----------|------|------|
| 網關 | 這個角色能不能碰這條路由 | 只需要 Token 裡的身分資訊 | `AccessPolicyChain` + 設定檔規則 |
| 服務 | 這筆資料是不是他的、這個狀態能不能改 | 需要查業務資料庫 | `@RequiresPermission` + 服務內的業務邏輯 |

判準很明確：**網關手上沒有業務資料，也不該為了授權去查業務資料庫。**
一旦網關開始查訂單表來判斷「這張訂單是不是他的」，它就不再是網關了。

## 責任鏈與 ABSTAIN

`AccessPolicy` 回傳 `PERMIT` / `DENY` / `ABSTAIN` 三值而非布林。
`ABSTAIN` 是這個模型的關鍵：它讓每個策略只回答自己管得到的部分。
沒有棄權語意的話，每個策略都被迫對全域規則表態，策略之間就再也無法獨立演進。

`AccessPolicyChain` 接受所有 `AccessPolicy` 型別的 Bean，因此要加入 IP 白名單、
營業時間限制或 OPA 遠端判定，只需新增一個 Bean 並指定 `order()`，
既有程式碼一行都不用改。

## 預設判定：DENY（fail-closed）

所有策略都棄權時的兜底值預設為 `DENY`。

**代價是真實存在的。** 開發過程中就遇到一次：`/auth/logout` 需要「已登入」但不需要任何
特殊權限，因為沒有對應規則而落到兜底的 `DENY`，回了 403。
解法是為它明確加一條無條件規則，而不是把預設改成 `PERMIT`。

這正是選擇 fail-closed 的理由：**失敗的方向是對的。**
漏配規則的後果是一個立刻會被發現的 403，而不是一條沒人注意到、對外裸奔的端點。

若團隊採「網關只做認證、授權全部下放服務」的分工，可將
`gateway.auth.authorization.default-decision` 改為 `PERMIT`，
但那等於把最後一道防線交給每一個微服務各自把關 —— 只要有一個服務忘了檢查，就是一個缺口。

## 後果

- 正面：網關不需要理解業務語意，維持輕薄。
- 正面：兩層規則重疊形成縱深防禦，繞過網關的直連請求仍被服務端擋下。
- 負面：路徑規則與後端 API 之間存在耦合，新增路由必須同步更新網關設定。
  緩解方式是規則按路徑前綴分組（`/api/orders/**` 一組），
  而不是為每個端點各寫一條 —— 網關的規則本來就該是粗粒度的。
- 負面：權限碼在網關設定與服務註解中各出現一次。這是刻意的重複：
  兩者的失效模式不同（一個防外部流量、一個防繞過網關），合併會失去縱深防禦的意義。
