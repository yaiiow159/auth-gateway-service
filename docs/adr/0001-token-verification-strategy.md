# ADR-0001：網關以本地驗簽為主，遠端自省為可切換備援

- 狀態：已採納
- 日期：2026-08-28

## 背景

網關位於所有流量的必經路徑上，每個請求都必須確認憑證的有效性。
驗證方式的選擇會直接決定整站的延遲下限與可用性上限。

## 選項

**A. 每個請求呼叫授權中心（自省 / RPC / gRPC）**

- 優點：權限異動與撤銷可即時生效；支援不透明 Token，憑證內容不外洩。
- 缺點：每個請求多一次網路往返；授權中心成為全站的同步依賴，它一慢，所有請求跟著慢，它掛了，全站癱瘓。要緩解就得加快取與斷路器，於是又回到「快取一致性」這個原本想避開的問題。

**B. 網關以 JWKS 公鑰在本地驗簽**

- 優點：零網路往返，驗簽是純 CPU 運算；授權中心不在關鍵路徑上，它短暫離線只影響「登入與換發」，不影響既有工作階段。
- 缺點：JWT 本質上無法撤銷，權限異動要等到 Token 過期才生效。

## 決策

**採 B，並以兩個機制補上它的缺口：**

1. **短命 Access Token**（預設 10 分鐘）——把權限異動的最大延遲壓在可接受範圍。
2. **Redis 撤銷名單**——登出與強制下線可即時生效。查 Redis 雖然仍是一次網路往返，但它是快取層而非業務服務，延遲低一個數量級，且失敗時可依 `fail-open` 設定降級。

選項 A 以 `RemoteIntrospectionTokenVerifier` 保留為可切換的實作，透過
`gateway.auth.verification-mode: REMOTE` 啟用。它存在的意義不是「以防萬一」，
而是把「驗證方式」明確標示為一個可替換的決策點：當需求變成「權限異動必須秒級生效」
或「改用不透明 Token」時，切換設定即可，過濾器、授權策略與身分注入完全不受影響。

## 後果

- 正面：驗證延遲從「一次 RPC」降到「一次 CPU 運算」；授權中心的可用性與整站可用性解耦。
- 負面：權限異動最長延遲一個 Access Token 的壽命。若某個場景無法接受，正確做法是對該使用者主動撤銷 Token 強制換發，而不是把全站改成遠端驗證。
- 負面：JWT 攜帶權限清單，權限極多的使用者會讓 Header 變大。若出現這種情況，應改為只放角色、由服務端展開權限。

## 補充：`fail-open` 的取捨

撤銷名單查詢在 Redis 不可用時的行為由 `gateway.auth.revocation.fail-open` 決定：

- `true`（預設）：查不到就當作未撤銷。已登出的短命 Token 可能在剩餘壽命內仍可用，但站台不會因為 Redis 抖動而全面癱瘓。
- `false`：一律拒絕。安全性最高，代價是快取層變成單點故障。

預設選 `true`，因為 Access Token 的壽命本來就只有幾分鐘，風險窗口有限。
金流、後台等高敏感部署應改為 `false`，並為 Redis 建置高可用。
無論哪一種，查詢失敗都會留下錯誤日誌以便告警。
