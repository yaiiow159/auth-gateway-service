# ADR-0002：以 Header 傳遞身分，並加上 HMAC 簽章

- 狀態：已採納
- 日期：2026-08-28

## 背景

網關驗證完憑證後，必須把身分傳給下游微服務。傳遞方式決定了下游能不能安全地信任它。

## 選項

**A. 直接轉發原始 JWT，由每個服務自行驗證**

每個服務都得引入 JOSE 函式庫、設定 JWKS 位址、處理金鑰輪替。
換簽章演算法或加 MFA 等級時，所有服務都得改。認證邏輯被複製了 N 份，
只要有一份寫錯（例如漏驗 `audience`）就是一個漏洞。

**B. 網關解析後以明文 Header 傳遞（`X-User-Id` 等）**

服務端極度簡單，但安全性完全建立在「除了網關，沒有人碰得到這個服務」這個網路層假設上。
一次 Service Mesh 設定失誤、一個被打穿的 Sidecar，攻擊者就能直接送出
`X-User-Id: 1` 冒充管理員。

**C. 明文 Header + 網關 HMAC 簽章**

保留 B 的簡單性，同時讓下游具備獨立驗證能力。

## 決策

**採 C。** 具體規則：

1. **先剝除，再注入。** `IdentityPropagator` 對**每一個**請求（含免認證路徑）
   無條件移除 `AuthHeaders.CLIENT_FORGEABLE` 中的所有 Header，之後才寫入可信身分。
   若只在認證成功時才消毒，攻擊者只要挑一條公開端點就能把偽造 Header 送進後端。
2. **簽章涵蓋完整身分內容與時間戳**，格式為 `<epochSecond>.<Base64Url(HMAC-SHA256)>`。
   角色與權限先排序再串接，否則同一份身分會因 `Set` 的迭代順序不同而產生不同簽章。
3. **簽章與驗章共用 `auth-contract` 中的同一份實作**，兩端邏輯不可能分岔。
4. **下游「有身分就必須有正確簽章」**：出現 `X-User-Id` 卻無法驗章時一律拒絕（401），
   而不是降級成匿名 —— 降級會讓攻擊者得以用偽造 Header 試探哪些端點允許匿名存取。
5. **非 ASCII 內容以 URL encoding 寫入 Header**（HTTP Header 只保證承載 ASCII，
   中文暱稱直接塞入輕則亂碼、重則被代理截斷）。簽章計算的是編碼前的原始值。

## 後果

- 正面：下游服務完全不需要認識 Token、金鑰或 JWKS，認證機制的演進不會擴散出去。
- 正面：即使網路隔離失效，偽造請求仍會被下游擋下（零信任）。
- 負面：多了一個必須在網關與所有服務間保持同步的共享密鑰。緩解方式是啟動期強制檢查——
  啟用簽章卻未設定密鑰時，服務直接啟動失敗。
- 負面：HMAC 是對稱式的，任何持有密鑰的服務理論上都能偽造身分。
  若信任邊界需要再收緊，可改為以網關私鑰簽章、服務端以公鑰驗證，
  代價是驗章成本從 HMAC 升為非對稱運算。
- 時間戳限制了簽章的重放窗口（預設 60 秒），該值同時要吸收服務間的時鐘偏移，不宜設得太小。
